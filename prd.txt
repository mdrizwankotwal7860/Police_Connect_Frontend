1. Product Overview
Police Connect is a polished, responsive frontend for an online police complaint management and tracking platform. The frontend should simulate complete citizen, police officer, station-admin and super-admin experiences using realistic mock data. It must be architected so a real API can be connected later without redesigning the UI.
2. Frontend Goals
Create a trustworthy, modern public-safety/government-style interface.
Make complaint submission simple and mobile-friendly.
Provide clear complaint tracking and status visibility.
Provide professional police operations dashboards.
Provide management analytics and administrative interfaces.
Use reusable components and a clean, scalable frontend architecture.
Keep all current data interactions mock/local so the project works without a backend.

4. Visual Identity
The interface must communicate TRUST, SAFETY, SECURITY and ACCOUNTABILITY. It should look like a premium government/public-service SaaS platform, not a generic CRUD dashboard.
Primary visual direction: deep navy/police blue, white, slate neutrals and restrained muted-gold accents.
Use red sparingly for critical alerts/errors and green for successful/resolved states.
Use clean typography, generous spacing, cards, subtle shadows, professional icons and restrained animations.
Avoid neon colors, excessive gradients, cartoon styling and excessive motion.
Support light mode as the primary design. If implemented, dark mode should remain professional and accessible.
5. Hero Visual Requirements
The landing-page hero is a key visual element.
Include a high-quality police station image.
Include a police cap image as a recognizable law-enforcement/public-service symbol.
Include a subtle secured firearm/law-enforcement visual, presented professionally and non-violently.
Never show active firing, threatening poses, gore or violent scenes.
Composition should feel cinematic and official: police station background, cap/desk foreground and subtle law-enforcement/security cues.
Use responsive image cropping so the composition remains attractive on mobile.

18. Mock Data Architecture
Do not hard-code data directly inside UI components. Create typed mock data and a mock service layer.
Suggested structure:src/  app/  components/  features/    auth/    complaints/    police/    admin/  data/    mockUsers.ts    mockStations.ts    mockOfficers.ts    mockComplaints.ts    mockNotifications.ts  services/    mockAuthService.ts    mockComplaintService.ts    mockOfficerService.ts    mockAdminService.ts  types/  lib/  hooks/
The service functions should return Promise-like results so they can later be replaced with real API calls without rewriting page components.
19. Mock Complaint Lifecycle

Complaint appears in citizen's complaint list.
Police dashboard shows the complaint in its queue.
Officer can simulate assignment/investigation/status updates.
Citizen tracking page reflects the updated mock status.
Every simulated status update appears in the timeline.

21. Responsive Requirements
Mobile-first implementation.
Citizen complaint form optimized for one-handed/mobile use.
Desktop dashboards use sidebar + content layout.
On mobile, sidebar becomes a drawer/bottom-friendly navigation.
Tables must remain usable with responsive scrolling or card transformation.
Charts resize without clipping.
Hero imagery and text stack cleanly on small screens.
22. Accessibility
Semantic HTML.
Keyboard navigation.
Visible focus states.
Proper form labels.
Accessible modal behavior.
Accessible status badges and timeline text.
Minimum practical color contrast.
Do not communicate important state by color alone.
Respect reduced-motion preferences.
23. Animation & Interaction
Use subtle page/section reveal animations.
Card hover elevation should be restrained.
Timeline transitions may animate softly.
Use skeletons instead of blocking spinners where possible.
Respect prefers-reduced-motion.
Avoid animation that delays task completion.
24. Frontend Security/Privacy UX
Never display passwords or tokens.
Mask sensitive contact information where appropriate.
Show clear session/logout controls.
Evidence previews must not imply public access.
Use confirmation for destructive/consequential actions.
Clearly label demo/mock data so it cannot be mistaken for real police records.
25. Frontend Performance
Use Next.js image optimization.
Lazy-load heavy images/charts where appropriate.
Avoid unnecessary client components.
Memoize expensive table/chart transformations where needed.
Paginate mock tables to simulate production behavior.
Keep reusable UI components lightweight.

30. AI Coding Agent Prompt
Build the frontend described in this PRD as a complete, polished Next.js + TypeScript application. Do NOT create a backend, PostgreSQL database, FastAPI service, Docker backend or real API dependency. Use realistic typed mock data and an isolated mock service layer. The architecture must make it easy to replace mock services with REST APIs later.Prioritize visual quality and usability. Build the citizen complaint experience, police officer workspace, station-admin dashboard and super-admin dashboard as coherent products with shared design components. Implement responsive behavior, accessibility, validation, loading states, empty states, error states, confirmation dialogs, realistic charts and professional police/public-service branding.Use police station imagery, police cap imagery and a subtle, professional, non-violent firearm/law-enforcement visual in the hero. Do not depict active violence.Do not stop at a landing-page mockup. Implement all routes, screens and interactions specified in this PRD. Avoid putting large hard-coded datasets inside components. Keep data in typed mock files and business-like mock service functions. At the end, verify all critical user journeys and ensure the project runs without a backend.
31. Final Frontend Flow
Landing → Register/Login → Citizen Dashboard → File Complaint → Review → Submit → Complaint ID → Track → Police Queue → Officer Investigation → Status Update → Citizen Timeline → Resolution
